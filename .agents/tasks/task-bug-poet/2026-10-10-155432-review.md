# Bug 诗人（Bug Poet）完整实现

这次提交实现了整个 Bug 诗人应用，包括后端 Express+TypeScript 服务（LLM 调用、格式校验、重试逻辑、兜底诗）、前端 React+TypeScript+Vite 应用（诗体选择、输入面板、古风竖排展示、历史诗集、PNG 导出）以及根工作区的 npm workspaces 配置。三条验证命令全部通过：后端 tsc 构建 exit 0，前端 vitest 15/15 pass，前端 vite build exit 0 并产出 dist/。

Watch for: LLM 超时逻辑存在双重超时隐患——后端与前端各自设置了 10 秒 abort，但二者使用的是 Promise.race，不存在缓冲，若服务端先超时则客户端的 fetch 信号永远不会触发真正的中断（confirmed）。前端在 fallback 响应时同时设置 errorMessage 和 poemResult，但渲染层的条件 `!poemResult.fallback` 阻止 PoemDisplay 渲染，意味着兜底诗永远不会显示在页面上（confirmed）。

**Verdict**: NEEDS_CHANGES

## High-level view

后端将 API Key 完全隔离在环境变量中，`OPENAI_API_KEY` 仅以 `process.env` 引用出现在 `llm.ts` 一处，前端代码和版本库中均无任何 key 值。速率限制配置为每 IP 每分钟 10 次，与规格完全匹配。

`calcAestheticScore` 是无 import 的纯函数，单元测试完整覆盖了 15 个用例，包括边界值和组合场景。`getScoreLabel` 的三个区间（≤30/≤70/>70）与需求规格完全一致。

PoemDisplay 使用 `writing-mode: vertical-rl` 实现竖排展示，媒体查询在 600px 以下降级为横排居中——这两点与规格完全吻合。

LLM 系统提示词、重试逻辑（最多 2 次）和兜底诗返回路径均已实现，但存在一个渲染层 bug：兜底诗的 `PoemDisplay` 永远不会渲染给用户看。前端 10 秒 AbortController 与后端 `Promise.race` 10 秒 timeout 并行存在，正常情况下不冲突，但后端超时后会把异常转成兜底诗 JSON 返回给前端，前端不会触发 `AbortError`——行为符合预期，但两层 timeout 值耦合，没有任何文档说明。

<summary>Issues (2)</summary>

1. **兜底诗不可见** — `App.tsx` 第 53 行在 `data.fallback` 为 true 时调用 `setPoemResult(data)`，但渲染条件是 `poemResult && !poemResult.fallback`，导致兜底诗的 `PoemDisplay` 永远被跳过。用户只看到 errorMessage 字符串，看不到兜底诗内容。需求 3.5 要求"显示一首内置的兜底诗"。修复：在 fallback 分支中去掉 `setPoemResult(data)` 并单独渲染兜底诗，或移除 `!poemResult.fallback` 条件，让 PoemDisplay 在 fallback 时也渲染。

2. **前后端双重超时值硬耦合无说明** — 后端 `llm.ts` 在 `Promise.race` 中硬编码 10s timeout，前端 `App.tsx` 也硬编码 10s AbortController。若后端先超时并成功返回兜底诗 JSON，前端 abort 信号不会触发，行为正确；但若后端 LLM 调用被挂起（例如 TCP 保活但不响应），两个 10s timer 会在同一时刻到期，前端抛 AbortError、后端抛 timeout 各自处理，互不知晓。两个值没有注释或文档说明其刻意对齐。建议在代码中加注释说明两层超时的设计意图，或将前端 timeout 设为 12s 给后端留缓冲。

### 兜底诗渲染路径断裂

`App.tsx` 处理 fallback 响应的分支如下：

```tsx
if (data.fallback) {
  setErrorMessage(data.message || '诗人今天罢工了')
  setPoemResult(data)   // 设置了，但…
} else {
  setPoemResult(data)
  savePoem(...)
}
```

渲染层：

```tsx
{poemResult && !poemResult.fallback && <PoemDisplay ... />}
```

`data.fallback === true` 时，`setPoemResult(data)` 将结果存入状态，但 `!poemResult.fallback` 条件阻止 PoemDisplay 渲染。用户只能看到错误提示文字，无法看到兜底诗的正文、诗名、自注。需求 3.5 明确要求"显示一首内置的兜底诗"而不仅仅是提示语。这是 confirmed 的功能缺失。

### 前后端双重超时耦合

后端 `llm.ts`（第 143 行）对 OpenAI 调用施加 10s `Promise.race`，超时后抛出异常，`generatePoem` catch 块返回兜底诗 JSON（`fallback: true`）。前端 `App.tsx`（第 36 行）对整个 fetch 施加 10s AbortController。

两层超时值相同，没有任何缓冲：后端处理时间（鉴权、JSON 序列化、网络）占用了部分时间窗口，前端 10s 窗口实际上比后端短。在慢速网络下，后端可能在 9.8s 时才开始写响应，前端已在 10s 处 abort，导致前端报 `AbortError`（超时兜底），而非收到后端精心准备的兜底诗。建议前端 timeout 设为 15s，并加注释说明意图（possible，取决于实际网络延迟分布）。
